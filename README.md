# 烘焙试配稳定性与风味标注范围

豆批和成品重量用千克，分数越高代表相应风味越强。物料的 source_origin 表示需要实证对应的原料来源。 所有资料均为合成记录。文件编码为 UTF-8，数字、日期及标记在原始记录中均以字符串保存。问号表示来源未能提供该值；加号分隔来源系统使用的组合编号。

## 资料

green 的 stock 为开始投料前的实有重量，母批重量包含已经拆分的子批数量。label 的 range_max 应用于档案允许重复条件下每项风味的分数跨度，min_days 是独立试烘日数。已发包装凭据是外部交付事实，待发包装仍在本厂。

- `green.json` 记录字段为 `lot`、`origin`、`grade`、`stock`、`split_parent`。
- `roasts.json` 记录字段为 `test`、`lot_a`、`lot_b`、`ratio_a`、`profile`、`day`、`blind`。
- `cups.json` 记录字段为 `blind`、`judge`、`rep`、`fruit`、`bitter`、`version`、`state`。
- `labels.json` 记录字段为 `label`、`fruit_min`、`bitter_max`、`range_max`、`min_days`。
- `work.json` 记录字段为 `order`、`lot_a`、`lot_b`、`ratio_a`、`weight`、`label`、`state`、`finished`。
- `splits.json` 记录字段为 `parent`、`child`、`kg`、`state`。
- `shipments.json` 记录字段为 `finished`、`package`、`weight`、`label`、`state`。
- `channels.json` 记录字段为 `channel`、`package`、`declared`、`label`、`version`、`delivered`。
- `blends.json` 记录字段为 `blend`、`uses`、`weight`、`packaging`、`revision`、`state`。
- `review_actions.json` 记录字段为 `at`、`kind`、`ref`、`detail`。

## 评估模型（src/）

代码按证据链分层，全部为纯函数，可对同一资料目录反复重放；新原料或返测落盘后重跑同一组命令即可得到新结论。

| 模块 | 职责 |
| --- | --- |
| `parse.js` | 字符串/问号解析、组合编号拆分、引用与守恒核对 |
| `evidence.js` | 盲评汇总、候选（豆批+配比+烘焙档案）聚合、三类波动分解、换批差值 |
| `labels.js` | 档案下限/上限/重复跨度/独立试烘日的合取判定 |
| `availability.js` | 豆批台账（拆分、事实投料、未投料待承诺）与守恒检查 |
| `work.js` | 订单级证据+实物可兑现性、未投料替换候选、库存保留指示 |
| `traceability.js` | 证据→成品→包装→渠道追溯、召回处置、总批/子批口径、混配不可逆规则 |
| `review.js` | 撤回/找回边界翻转、事件分流（常规补试/重新声明/渠道更正）、历史重放 |
| `procurement.js` | 候补试烘优先级、按豆批或成品批查询、三种不能兑现情形归类 |
| `report.js` / `cli.js` | 文本与 JSON 报告、命令行入口 |

### 固化的业务规则

1. **证据口径**：仅 `state=记入` 的杯测进入统计；撤回杯测即使数值与记入行相同也剔除。同一盲评号多版本时，撤回/找回只作用于最高版本。
2. **候选口径**：候选键是两支具体豆批 + 配比 + 烘焙档案。同产区同规格的新豆批（含母批与拆分子批之间）不共享证据，没有对应试烘即「未试到」。
3. **波动三分**：评委分歧（评委均值跨度）、同一试烘重复杯（同评委 rep 跨度）、跨试烘日漂移分别度量；换批真实变化只在同配比同档案、仅换 A 豆批的候选之间比较。
4. **档案合取**：果香均值下限、苦感均值上限、两项风味的重复跨度、独立试烘日数必须同时满足；单项高分不能抵消另一项超限。风味超限与证据不足分别列示，证据不足只能进候补试烘，不能形成销售声明。
5. **物料事实**：母批可用量先扣已拆公斤数，再扣已投料/已包装的事实消耗；未投料只作待承诺。已投料实际组成不可替换，未投料可改投合格候选。
6. **守恒**：混配拆分或换包装不得产生新的合格公斤数，`check` 对包装累计超产量、混配产出超投入做拦截。
7. **召回口径**：总批渠道在确认实际子批前，按可追溯最小范围整体停用标注；子批渠道精确到包装；无关姐妹批与其他标注继续交付。已混且不可拆的库存永久退出该标注，母批其他合格子批不受影响。
8. **事件分流**：新结果区分「需要常规补试」「需要重新作声明」「需给已收到旧版本的确切渠道作更正」三类，并联动重算未投料指示与补试日数。

## 命令行

```sh
node src/cli.js <命令> [--data ./data] [--json]
```

- `check`：资料引用与公斤守恒核对。
- `candidates`：候选配比的感官均值、跨度、波动分解、档案判定与换批差值。
- `orders`：每张生产单的证据状态、受阻原因（原料不足/未试到/风味证据失效）、替换候选与出货指示。
- `ledger`：豆批实物台账。
- `recall --blind V1 --label L1`：盲评证据变化的完整召回处置面。
- `boundary --blind V1 --label L1`：模拟该盲评撤回/恢复后哪些候选跨过声明边界。
- `backup`：采购候补试烘表（按对当前出货/声明的影响排序，含需补独立试烘日数）。
- `query <豆批或成品批>`：实物可用量、证据来源、关联订单与待查范围。
- `events`：重放 `review_actions.json` 的历史确认。
- `event --kind 撤回杯测|找回样|换豆|重新装包|渠道收悉 --ref ...`：单次事件分流。

## 运行

使用 Node.js 22。项目无需下载第三方依赖。

```sh
npm ci --offline --ignore-scripts
npm test
npm run scenario   # 换豆→复评撤回→重新装包→渠道收悉的完整演练
npm run report     # 候选/订单/台账/候补表的当前结论
```

`npm run data:check` 检查合成资料能否读取并核对相关记录的引用。资料校验脚本可以独立运行。
